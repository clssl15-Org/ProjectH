# [설계] 0529 UI 화면 커서 표시 정책

작성일: 2026-05-29

---

# 범위

게임 플레이 화면에서는 마우스 커서를 숨기고, ESC로 여는 설정창이나 유물/가이드처럼 포인터 조작이 필요한 UI 화면에서만 커서를 보이게 하는 정책을 정리한다.

이번 문서는 구현 전 설계 기록이며, 선택 방향은 별도 `CursorVisibilityController`를 두는 방식이다.

---

# 현재 구조

관련 코드:

- `Assets/Scripts/Game/Stage/StageManager.cs`
- `Assets/Scripts/Infrastructure/InputHandling/InputHub.cs`
- `Assets/Scripts/Infrastructure/InputHandling/Interfaces.cs`
- `Assets/Scripts/UI/Views/SettingsUI.cs`
- `Assets/Scripts/UI/Views/RelicInfoPanelUI.cs`
- `Assets/Scripts/UI/Views/GuideAndWorldRecordsUI.cs`
- `Assets/Scripts/UI/Views/RelicAcquisitionUI.cs`

`StageManager`는 씬 시작 시 `InputHub`를 가져오고, 플레이어와 UI 입력 주체를 등록한다.

- `Player`, `PlayerUI`를 `InputHub`에 등록한다.
- `SettingsUI.GetOpenerSubject()`를 등록해 ESC 설정창 열기 입력을 관리한다.
- `RelicInfoPanelUI.GetOpenerSubject()`를 등록해 유물 정보창 열기 입력을 관리한다.
- `SettingsUI`, `RelicInfoPanelUI`, `GuideAndWorldRecordsUI`, `RelicAcquisitionUI`에는 `IInputLayerController.Initialize(InputHub)`로 `InputHub`를 전달한다.

각 UI는 열릴 때 `InputHub.Block(this)`를 호출하고, 닫힐 때 `InputHub.Unblock(this)`를 호출한다. 설정창은 ESC로 열리고 닫히며, 유물 정보창과 가이드/월드 기록창도 UI가 열려 있는 동안 다른 입력을 막는 구조를 갖는다.

---

# 판단

`InputHub`에 직접 커서 표시 책임을 넣는 것은 적절하지 않다.

이유:

1. `InputHub`의 현재 책임은 입력 레이어의 허용/차단 여부를 평가하는 것이다.
2. `InputHub.Block()`은 UI뿐 아니라 포탈 이동, 화면 암전, 연출 중 입력 잠금에도 사용될 수 있다.
3. 따라서 `Block 상태 == 커서 표시`로 해석하면, 실제 UI가 아닌 연출 잠금에서도 커서가 보일 수 있다.
4. 커서 표시 여부는 "입력이 막혔는가"보다 "포인터 조작이 필요한 UI가 열려 있는가"에 가까운 정책이다.

따라서 `StageManager`를 연결 지점으로 사용하되, `InputHub` 자체를 커서 관리자처럼 확장하지 않는다.

---

# 선택 방향

별도 `CursorVisibilityController`를 만든다.

역할:

- 게임 플레이 상태에서는 커서를 숨긴다.
- 포인터 조작이 필요한 UI가 열리면 커서를 보인다.
- 여러 UI가 겹쳐 열릴 수 있으므로, 요청자를 기준으로 표시 요청을 누적 관리한다.
- 마지막 UI가 닫힐 때만 커서를 다시 숨긴다.

예상 동작:

```csharp
// UI 열림
Cursor.visible = true;
Cursor.lockState = CursorLockMode.None;

// 플레이 화면
Cursor.visible = false;
Cursor.lockState = CursorLockMode.None;
```

2D 액션 게임 기준으로는 `CursorLockMode.Locked`까지 사용할 필요는 낮다. 마우스 시점 회전이 있는 게임이 아니므로, 커서를 화면 중앙에 고정하기보다 숨기는 정도가 자연스럽다.

# 구현 방향

## 1. 커서 컨트롤러 추가

예상 파일:

- `Assets/Scripts/UI/CursorVisibilityController.cs`

예상 형태:

```csharp
using System.Collections.Generic;
using UnityEngine;

namespace UI
{
    public class CursorVisibilityController
    {
        private readonly HashSet<object> _showRequesters = new();

        public void HideForGameplay()
        {
            _showRequesters.Clear();
            Apply();
        }

        public void Show(object requester)
        {
            if (requester != null)
                _showRequesters.Add(requester);

            Apply();
        }

        public void Hide(object requester)
        {
            if (requester != null)
                _showRequesters.Remove(requester);

            Apply();
        }

        private void Apply()
        {
            Cursor.visible = _showRequesters.Count > 0;
            Cursor.lockState = CursorLockMode.None;
        }
    }
}
```

`MonoBehaviour`로 둘 수도 있지만, 현재 UI들은 `StageManager`에서 명시적으로 연결되는 구조이므로 단순 서비스 객체로 시작해도 충분하다.

## 2. UI에 커서 컨트롤러 전달

`SettingsUI`, `RelicInfoPanelUI`, `GuideAndWorldRecordsUI`, `RelicAcquisitionUI` 중 실제 포인터 조작이 필요한 UI에 커서 컨트롤러를 전달한다.

선택지는 두 가지다.

1. 각 UI에 `Initialize(IInputHub inputHub, CursorVisibilityController cursor)` 형태의 별도 초기화 메서드를 추가한다.
2. 기존 `IInputLayerController.Initialize(IInputHub inputHub)`는 유지하고, 커서용 인터페이스를 별도로 둔다.

기존 인터페이스의 의미를 흐리지 않기 위해 2번이 더 안전하다.

예상 인터페이스:

```csharp
namespace UI
{
    public interface ICursorVisibilityControllerUser
    {
        void Initialize(CursorVisibilityController cursorVisibilityController);
    }
}
```

## 3. UI 생명주기에 연결

각 UI의 `IEnablable.OnEnabling`에서:

```csharp
_cursorVisibilityController?.Show(this);
```

각 UI의 `IEnablable.OnDisabling`에서:

```csharp
_cursorVisibilityController?.Hide(this);
```

이렇게 하면 설정창에서 유물 정보창으로 넘어가거나, 한 UI가 다른 UI를 여는 흐름에서도 커서 표시 요청이 UI 단위로 관리된다.

## 4. StageManager 연결

`StageManager.Start()`에서 컨트롤러를 생성하고 UI에 전달한다.

예상 흐름:

```csharp
var cursorVisibilityController = new CursorVisibilityController();
cursorVisibilityController.HideForGameplay();

if (SettingsUI is ICursorVisibilityControllerUser settingsCursorUser)
    settingsCursorUser.Initialize(cursorVisibilityController);

if (RelicInfoPanelUI is ICursorVisibilityControllerUser relicCursorUser)
    relicCursorUser.Initialize(cursorVisibilityController);

if (GuideAndWorldRecordsUI is ICursorVisibilityControllerUser guideCursorUser)
    guideCursorUser.Initialize(cursorVisibilityController);

if (RelicAcquisitionUI is ICursorVisibilityControllerUser acquisitionCursorUser)
    acquisitionCursorUser.Initialize(cursorVisibilityController);
```

게임 씬에 들어온 직후에는 `HideForGameplay()`로 기본 상태를 플레이 화면에 맞춘다.

# 적용 대상 UI

우선 적용 후보:

1. `SettingsUI`
   - ESC 설정창
   - 버튼, 스크롤바 조작이 있으므로 커서 표시가 필요하다.
2. `RelicInfoPanelUI`
   - 유물 정보창
   - UI 조작이 필요한 창이므로 커서 표시 대상이다.
3. `GuideAndWorldRecordsUI`
   - 설정창에서 열리는 가이드/기록 UI
   - ESC로 닫히며 UI 조작 가능성이 있으므로 커서 표시 대상이다.
4. `RelicAcquisitionUI`
   - 유물 획득 UI
   - 실제 마우스 조작이 필요하지 않은 연출형 UI라면 제외할 수 있다.
   - 선택지가 있거나 버튼/상호작용이 있다면 포함한다.

`PlayerUI`는 게임 플레이 HUD 성격이므로 커서 표시 대상에서 제외한다.

# 주의사항

1. `InputHub.Block()` 호출을 커서 표시 조건으로 직접 사용하지 않는다.
2. UI가 `Disable()`되기 전에 다른 UI를 여는 흐름에서는 커서 표시 요청 순서가 꼬이지 않도록 요청자별 집합으로 관리한다.
3. 씬 전환이나 `StageManager.OnDestroy()` 시점에는 커서 상태가 다음 씬에 남지 않도록 새 게임 씬 시작 시 `HideForGameplay()`를 호출한다.
4. 타이틀 화면은 메뉴 조작이 기본이므로 별도 정책이 필요하다. 이번 문서의 우선 범위는 게임 플레이 씬이다.
5. Unity Editor에서는 플레이 모드 종료 후 커서 상태가 남아 보일 수 있으므로, 필요하면 `OnDestroy()`에서 `Cursor.visible = true`로 복구하는 Editor 전용 처리를 별도로 검토한다.

# 결론

이번 요구사항은 `InputHub`의 입력 차단 상태에 직접 묶기보다, 포인터 조작이 필요한 UI의 열림/닫힘 생명주기에 커서 표시 요청을 연결하는 방식이 적절하다.

`StageManager`는 연결 지점으로 사용하고, 실제 커서 상태 관리는 별도 `CursorVisibilityController`가 담당한다. 이렇게 하면 ESC 설정창뿐 아니라 유물 정보창, 가이드/기록 UI처럼 다른 UI가 추가되어도 커서 표시 정책을 한곳에서 일관되게 유지할 수 있다.

남은 수동 확인:

- 이름 입력 모드 진입 프레임에 커서가 먼저 보이고, 이어서 입력 필드가 바로 활성화되는지 확인한다.
- ESC 설정창, 유물 정보, 가이드/기록, 유물 획득 UI는 열릴 때 커서가 보이고 닫힐 때 숨겨지는지 확인한다.
- 포탈 이동, 암전, 입력 잠금처럼 UI가 아닌 `InputHub.Block()` 상황에서는 커서가 보이지 않는지 확인한다.
